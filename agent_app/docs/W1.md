# Q&A

**1、为什么要用分层架构，现在有哪些层，每个层的作用分别是什么？**

为什么要用分层，分层有哪些好处？

对于测试比较方便，比如BaseLLM这一层抽象，我们可以塞进去一个MockLLM进去，模型的真假事实上不会影响本周的对话逻辑；

替换方便，在绝大部分情况下，改动一个需求只需要改动一个文件；

可定位：报错从哪一层冒出来，就知道问题在哪一层。看报错名字就能定位报错层。

现在W1结束已经有的层：入口层（cli.py），编排层（loop，W1没有），能力层（tools,rag,compaction.py现在没有），会话层（session.py），模型层（llm.py），基础层（config.py,error.py,observability.py）

每层的作用：

基础层：底层配置比如APIKEY，异常类型与ToolResult协议，日志格式，tarce与TOKEN估计，这一层只能被依赖

模型层：lm.py：BaseLLM（一个抽象基类）+ DeepSeekLLM（一个具体实现）+ with_retry（重试装饰器）

这是全项目唯一知道DeepSeek的地方，如果换厂商只需要动它，只能依赖模型层，被下面的层依赖

会话层：session.py：messages（历史）+ session_id（身份）+ persona（人设）+ 存/读/清。

这一层管的是某个用户的全部会话历史，不需要管怎么聊的，也就是他不知道有模型这回事，一个Session类，三个方法：存+读+清理

能力层（还未建）

这一层是模型能用的手段集合，每个工具都是一个独立的小单元，失败要返回ToolResult而不是抛出异常。

编排层（还未建）

loop/是决定下一步做什么的地方，他是agent和普通程序的真正分界，普通程序里代码写死先调A再调B，agent就是模型自己决定下一步调什么，loop负责给他工具，收他决定、执行，把结果喂回去。

入口层

cli.py现在的功能是：装配，IO，管理生命周期

将来会另有一个api.py，是第二个入口，

如何验证是真的分层

方法一：删文件

删了某层的文件，只能有更上层的文件报错，而下层的文件不应该报仇

方法二：对方法换实现

比如给llm.py换一个假的实现，看要改几个文件，如果一个都不用改，那就是真的分层

方法三：看import

只能是在上层里import下层，而不能有循环import。

**2、这一周我们实现了哪些层内的哪些功能，为后面铺垫了什么接口或者规范？**

基础层：

Settings类：以后所有层只能get_settings()，不能os.getenv()

并且预埋了后面才会用到的字段，事实上，这是一层层往上加的。

5、在当前实现下，一轮agent对话，或者说session，从创建到存储持久化进history.json的全部完整流程是什么？

三个阶段：启动-一轮对话-退出

阶段一：启动（内存从空到有数据）

DeepSeekLLM（）,造一个HTTP客户端，记住apikey与base_url，在这里不联网，不请求模型，顺带触发get_settings()第一次执行：读 .env → 构造 Settings → @lru_cache 缓存。之后全项目再调都是同一个对象。

Session.load()：去读 history.json。三种结果，文件不存在/文件损坏或者结构不对/正常

 如果 load() 返回 None，说明第一次运行。于是 Session(persona=...) 造个新的：随机 8 位 id + 1 条 system。

阶段二：一轮对话（list 从 N 条变成 N+2 条）

通过s.add_user(q)和s.add_assistant(reply)往messages里加信息，

for piece in llm.stream(s.messages) ← 唯一联网的一步。但是这个调用本身不发送请求，因为stream是生成器，只会返回一个生成器对象，真正发HTTP是循环第一次要第一个元素的那一刻。

6、在本周实现的各种函数或者数据结构中，有哪些是特别重要的？比如session或者message的结构

messages：list[{"role","content"}]

ToolResult：ok / content / error 把失败本身变成数据，而不是中断。ToolResult 是工具层和模型层之间唯一的信使。 工具的一切——成功、失败、为什么失败——都要经过它才能被模型看见。

Session对象：session_id + persona + messages

history.json：{session_id, messages}，注意messages是一个列表，元数据在外层，纯API数据在内层

Settings 的字段名：字段名 ↔ 环境变量名自动映射，改名就断连

模板：with_retry 和 trace 是同一个三层结构。

def 工厂(配置):                    # 第 1 层：收配置，import 时跑
    def decorator(func):           # 第 2 层：收函数，import 时跑
        @wraps(func)
        def wrapper(*args, **kwargs):   # 第 3 层：每次调用跑
            ...
        return wrapper
    return decorator

这两周只要写任何带参数的装饰器都是这样的模板。

label   = name or func.__name__
s.session_id = session_id or uuid4().hex[:8]
llm     = llm or DeepSeekLLM()

「外部给的优先，没有才用默认」。左边是可选值，右边是兜底。

**最重要的三条教训**

**① 每一项改动，都要有一个「能证明它对」的具体输出**

**可执行的规则不是「更细心」，而是：写完一个函数，立刻给一个具体输入，看输出对不对。没有这个，就不算写完。不是「等全部写完再联调」。是每个函数都有一次 py xxx.py 或者在 __main__ 里跑一下。**

**② 报错要读到「根因那一行」，不是最后一句**

**Traceback 从下往上看：最底下是表象，往上才是根因。**

**③ 「写成了另一个正确的东西」比写错更危险**

**"text" 加引号 → 语法对 return wrapper 缩进错 → 语法对 @with_retry() 挂 stream → 装饰器正常返回 llm = DeepSeekLLM() or llm → or 正常求值**

**四个都不报错，四个都等于白写。**

**写错会当场崩，写成了另一个正确的东西会一直活着，直到你依赖它的时候。**
