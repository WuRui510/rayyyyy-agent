## 一、环境：Docker Desktop + PostgreSQL

**Docker Desktop 是 Windows 上的三个东西的集合：**

- **图形界面** —— 看容器列表、看日志、改设置
- **CLI（`docker` 命令）** —— 在 PowerShell 里敲的那些
- **Engine** —— 真正跑容器的守护进程，藏在一个 WSL2 的 Linux 虚拟机里

为什么必须藏在 Linux 里：容器技术本质是 Linux 内核的 `namespaces` + `cgroups`。Windows 没有这两样，所以必须借一个 Linux 内核。

**在这个项目里，Docker 只做一件事：跑 PostgreSQL。**

### 为什么选 PostgreSQL，不选 MySQL / SQLite

因为项目核心是**读懂执行计划**，而 PostgreSQL 的 `EXPLAIN ANALYZE` 是业界最详细的之一。

```
Parallel Seq Scan on lineitem  (actual time=0.021..37.479 rows=185490 loops=3)
  Filter: (l_shipdate <= '1998-09-02')
  Rows Removed by Filter: 14422          ← MySQL 不告诉你这个
  Buffers: shared hit=2094 read=9464     ← SQLite 根本没有这个概念
```

| 数据库 | EXPLAIN 能给什么 |
|---|---|
| **PostgreSQL** | 节点类型、预估/实际行数、**实际耗时**、**过滤掉多少行**、**缓存命中/磁盘读** |
| MySQL | 节点类型、预估行数、`filtered` 百分比 —— 没有实际耗时 |
| SQLite | 只有"扫了哪个表、用了哪个索引" —— 信息量少一个数量级 |

Agent 靠这些数字判断瓶颈。**SQLite 给不出 `Rows Removed by Filter`，W4 的诊断能力就无米下锅。**

它装着 8 张 TPC-H 表、60 万行、**约 150 MB**（其中 `lineitem` 一张表就占 108 MB）。

## 二、数据：60 万行可复现的 TPC-H

### 最重要的一个决策：跳过 dbgen

原计划是"下载并编译 TPC-H 的 dbgen"。但 **dbgen 需要 C 编译器**，Windows 上没有；要么进 WSL 编译，要么拉 gcc 镜像——两种都可能吃掉一整天。

判断：dbgen 唯一多给的是「官方认证」三个字，而项目真正需要的是另外三样：

1. 字段名和类型严格照 TPC-H 官方 DDL
2. 数据量到 sf=0.1 的级别（lineitem 60 万行）
3. 数据分布合理（金额、日期、地区不是常数）

**这三样 Python 脚本 30 分钟能做完。**

真正需要正版数据的时机是 W8 放大到 sf=1 时，那时数据量的差异才有意义。

### 实际数字

| 表 | 行数 | 大小 |
|---|---|---|
| lineitem | 599,735 | 108 MB |
| orders | 150,000 | 22 MB |
| partsupp | 80,000 | 10 MB |
| part | 20,000 | 3.8 MB |
| customer | 15,000 | 3.1 MB |
| supplier | 1,000 | 0.4 MB |
| nation / region | 25 / 5 | 24 kB |

`orders` 一行是一笔订单头，`lineitem` 一笔订单 1~7 条明细。599,735 ÷ 150,000 ≈ 4，正好符合 TPC-H 规范。

### `SEED = 42` 不是随手写的

固定种子的唯一目的是：**每次生成的数据完全相同。** 因为 W8 要做「优化前 vs 优化后」的对比表——如果每次跑基准数据都不同，"28.4ms → 1ms" 就没有意义，可能只是这次数据恰好少。

### 另外两个决策

- **故意不建外键**：官方 dss.ddl 有，这里删了。导入 60 万行时外键检查会慢好几倍，而项目目标是看执行计划，不是验证数据完整性。主键保留（主键会自动建索引，影响执行计划，这是真实的）。
- **`.tbl` 输出无尾随分隔符**：让 `COPY ... WITH (FORMAT csv, DELIMITER '|')` 能直接吃，少一层转换。

## 三、工具层

### `tools/base.py` —— BaseTool 抽象

```python
class BaseTool(ABC):
    name: str = ""
    description: str = ""
    parameters: dict = {"type": "object", "properties": {}, "required": []}

    @abstractmethod
    def run(self, **kwargs) -> ToolResult: ...

    def to_schema(self) -> dict: ...      # 不是抽象方法
```

**三个类属性 + 两个方法**：

- `name` —— 工具的唯一名字，模型调用的就是它，注册表的 key 也是它
- `description` —— **全项目最重要的字符串**。模型没有别的信息判断该不该用这个工具，只有这段文字
- `parameters` —— JSON Schema，告诉模型要传什么
- `run()` —— 抽象方法，每个工具**实现各不相同**，所以必须抽象
- `to_schema()` —— 具体方法，每个工具**实现完全一样**（都是读三个属性、包成同一个形状），写一次就够

> **一条通用规则：抽象方法 = 每个子类都必须自己写、而且写得不一样的东西。**
> **能一次写好的通用逻辑，写进基类，不抽象。** 这叫模板方法模式。

### `tools/registry.py` —— 工具注册表

模型给名字，这里给对象。

**对每个实例，维护一个独立的「工具名 → 工具实例」字典。**

`self._tools = {}` 写在 `__init__` 里，所以每个 `ToolRegistry()` 实例有自己的字典，互不影响。

> ⚠️ 存的是**实例**，不是类。存类的话 `get("echo").run(...)` 会报
> `missing 1 required positional argument: 'self'`。

五个方法：

| 方法 | 做什么 |
|---|---|
| `register()` | 注册工具。重名抛 `ValueError`，没设 `name` 也抛 |
| `get()` | 按名字取，**取不到返回 `None`，不抛异常** |
| `all()` | 列出所有工具实例 |
| `to_schemas()` | 一次性拿到全部工具说明书，喂给 model 的 `tools=` 参数 |
| `__len__()` | 返回当前字典内工具数目 |

**两个方向相反的错误策略，是这周最重要的设计点：**

- `register` 重名 → **raise**（装配期的错误，必须当场发现）
- `get` 取不到 → **return None**（运行期的预期内情况，不能崩）

为什么不一致：模型幻觉出一个不存在的工具名是常态，应该由 `loop/` 转成一条错误消息喂回去；而两个工具都叫 `echo`，你永远不知道哪个会生效，必须在启动时就炸。

> **装配期失败要响，运行期失败要软。**

## 四、三条慢查询候选

写进 `infra/tpch/slow_queries.sql`。

| # | 形态 | 瓶颈 | 基线 | 优化手段 | 预期 |
|---|---|---|---|---|---|
| **A** | 高选择性过滤 | Seq Scan 60 万行只留 225 行 | **28.4 ms** | `INDEX(lineitem.l_shipdate)` | ~1 ms |
| **B** | 函数包裹列 | `date_trunc('month', o_orderdate)` | **36.8 ms** | **改 SQL + 建索引**（两步） | ~5 ms |
| **C** | 排序无索引 | top-N heapsort 扫全表 | **89.5 ms** | `INDEX(lineitem.l_extendedprice DESC)` | ~0.2 ms |

**B 是本项目最有教学价值的一条**：它的优化**不能靠加索引**——列被函数包了，加了也用不上。Agent 必须看 EXPLAIN 发现还是 Seq Scan，才会想到去改 SQL。**这就是「多轮优化」的天然案例。**

### 被淘汰的三条（同样值钱）

| 淘汰的 | 耗时 | 为什么不合格 |
|---|---|---|
| `l_shipdate <= '1998-09-02'` | 101.9 ms | **93% 选择性，索引救不了**，全表扫已是最优 |
| EXISTS 半连接 | 18.9 ms | 不够慢，且全缓存命中 |
| lineitem JOIN part 的 Hash Join | 115.5 ms | 慢，但**优化路径不清晰**，可能优化不动 |

> **判断该不该建索引，看的是「选择性」（扫多少行才返回一行），不是耗时。**
> 101.9 ms 比 28.4 ms 慢，但前者加索引会**更慢**。

## 五、「可重建的实验环境」为什么是核心

### 项目本质上是一个受控实验

不是"写个 Agent 让它跑"，而是：

> 同一条慢 SQL，优化前 28.4 ms，优化后 X ms —— 这个差值是我的 Agent 挣来的。

要让这句话成立，必须有 A/B 对比。而 A/B 对比的第一原则是：**除了要验证的那一个变量，其他一切必须完全相同。**

### 不可重建会毁掉整个项目

假设没有 Docker，只在本机装了个库，灌了数据：

- 第 1 天：跑基线，A 查询 28.4 ms
- 第 2 天：`CREATE INDEX ON lineitem(l_shipdate)`，变成 1.2 ms
- **现在库里有个索引了。再跑别的查询，基线已经变了**
- 想重测 A 的原始基线？先 `DROP INDEX` —— 但你确定只删了这一个吗？

三周之后，你手上有一堆数字，但不知道它们是在什么状态下测的。**对比表就废了——而对比表是项目唯一能证明价值的东西。**

### 具体是哪几层可重建

| 层 | 靠什么重建 | 耗时 |
|---|---|---|
| 数据内容 | `gen_data.py` 的 `SEED = 42` | ~10 秒 |
| 表结构 | `schema.sql` | ~1 秒 |
| 数据灌入 | 8 条 `COPY` | ~5 秒 |
| 整个数据库 | `docker compose down -v` + `up -d` + 上面三步 | **~30 秒** |

**任何时刻，你能在 30 秒内回到一个你完全知道状态的起点。**

### 三个"不可重建"就做不到的事

1. **敢让 Agent 乱来** —— W6 它要自己 `CREATE INDEX` / `DROP INDEX`，W7 可能写出把库拖死的 SQL。最坏情况是 `down -v` 重来
2. **每次实验都从已知状态开始** —— 测完 A 就重灌，再测 B。两条记录的基线才是同一口径
3. **别人能复现你的结果** —— `docker-compose.yml` + `gen_data.py` + `schema.sql` 就是环境的完整描述。面试官 clone 下来就能得到一模一样的 60 万行

> **"可重建"不是"方便"，是"实验结论成立的唯一前提"。**
> 没有它，对比表就是一张不知道在什么条件下测出来的数字表——看起来像证据，实际上不是。

## 六、这周踩的三个坑

### 1. `pg_stat_user_tables` 会骗你

查数据核验时，八个表全部 `n_live_tup = 0`、`last_analyze` 为空——看着像数据全丢了。

实际是：**统计收集器在服务器（容器）重启后清零**（PG 15+ 的 cumulative statistics 存在共享内存里）。

真正要查的是 `pg_class.reltuples`——它在系统表里，不会丢。

> **查「统计信息在不在」要看 `pg_class.reltuples`，不是 `pg_stat_user_tables`。**

### 2. 93% 选择性的查询，加索引会更慢

详见第四节。

### 3. `py tools/registry.py` → `ModuleNotFoundError`

| 运行方式 | `sys.path[0]` | 能 import `tools` 吗 |
|---|---|---|
| `py registry.py`（在 tools/ 里） | `agent_app/tools/` | ❌ |
| `py tools/registry.py`（在 agent_app 里） | `agent_app/tools/` | ❌ |
| `py -m tools.registry`（在 agent_app 里） | `agent_app/` | ✅ |

**包内模块的正确跑法：`cd` 到包外面一层，然后 `py -m 包名.模块名`。**
